# Исправление проблемы с непоследовательным поведением статусов экзаменов

## Проблема
При изменении дат экзаменов пользователем статус "Не подтвержден" устанавливается не всегда:
- На первом экзамене статус не установился
- На третьем экзамене сработал корректно

## Причина
Ограничение уникальности в таблице `approval_requests`:
```sql
CONSTRAINT unique_pending_exam_change UNIQUE (employee_id, exam_id, type, status)
```

Это ограничение блокирует:
1. Создание нового запроса, если уже существует pending запрос для того же экзамена
2. **Отклонение существующих запросов** (ошибка 23505 при смене статуса на 'rejected')
3. `pending_date` не устанавливается в `employee_exams`
4. Статус остается прежним

## СРОЧНОЕ ИСПРАВЛЕНИЕ
Если у вас сейчас ошибка при подтверждении/отклонении запросов, выполните НЕМЕДЛЕННО:
**`database/fix_pending_exam_requests.sql`** (содержит исправление ограничения уникальности)

## Решения

### Вариант 1: Автоматическое отклонение старых запросов (Рекомендуется)
Выполните SQL скрипт: `database/fix_pending_exam_requests.sql`

**Что делает:**
- Обновляет функцию `request_exam_date_change`
- Автоматически отклоняет существующие pending запросы перед созданием нового
- Очищает "зависшие" pending данные
- Гарантирует корректную установку статуса

### Вариант 2: Изменение ограничения уникальности
Выполните SQL скрипт: `database/alternative_fix_unique_constraint.sql`

**Что делает:**
- Заменяет ограничение уникальности на индекс
- Создает функцию "мягкого" обновления запросов
- Позволяет обновлять существующие pending запросы вместо создания новых

## Рекомендация
Используйте **Вариант 1**, так как он:
- Проще в реализации
- Более предсказуем в поведении
- Автоматически очищает старые данные
- Не требует изменения структуры базы данных

## Проверка исправления
После выполнения скрипта проверьте:

1. **Создайте тестового работника**
2. **Измените дату первого экзамена** → статус должен стать "Не подтвержден"
3. **Измените дату того же экзамена еще раз** → статус должен остаться "Не подтвержден"
4. **Проверьте, что уведомления отправляются администратору**

## Дополнительная диагностика
Для проверки состояния системы выполните:

```sql
-- Проверка pending запросов
SELECT 
    ar.id,
    ar.type,
    ar.status,
    ar.created_at,
    e.full_name as employee_name,
    ex.name as exam_name
FROM approval_requests ar
LEFT JOIN employees e ON e.id = ar.employee_id
LEFT JOIN exams ex ON ex.id = ar.exam_id
WHERE ar.type = 'exam_date_change' AND ar.status = 'pending'
ORDER BY ar.created_at DESC;

-- Проверка pending данных в экзаменах
SELECT 
    ee.id,
    e.full_name as employee_name,
    ex.name as exam_name,
    ee.exam_date,
    ee.pending_date,
    ee.pending_until
FROM employee_exams ee
JOIN employees e ON e.id = ee.employee_id
JOIN exams ex ON ex.id = ee.exam_id
WHERE ee.pending_date IS NOT NULL
ORDER BY ee.pending_until DESC;
```

2. Мониторьте количество pending запросов
3. Настройте автоматическую очистку старых данных
